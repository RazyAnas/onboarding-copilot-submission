# M9.6 — Companion UX (onboarding-first presence)

UI-layer only. Engine, flows, sessions, planner, and execution are untouched. The
one non-overlay addition is a thin read-only endpoint for Layer 1 (recommended
flows + completion status) — nothing in the hot path.

## Identity is behavior, not location

For a product embedded as a guest on someone else's page, iconic-ness cannot come
from owning a coordinate (we own none). It comes from a single continuous,
morphing object with a **completion ring**:

```
dormant  → nothing pending: invisible / minimal mark
resting  → docked progress pill (ring + "Set up Acme · 2 of 5")
open     → expands into the checklist (mission control)
guiding  → detaches → companion card + spotlight on the live target
asking   → summoned composer (center), no docked input ever
done     → ring closes → celebrates → retires to dormant
```

The ring filling toward done — a visible journey to value — is the signature. It
is recognizable in any dock position, which is why placement can be adaptive
without losing identity.

## Three layers

| Layer | Job | Surface | Footprint |
|---|---|---|---|
| 1 · Discovery | tell confused users what to do | adaptive progress dock → checklist | persistent-but-collapsed; self-retires at activation |
| 2 · Guidance | walk through a chosen flow | companion card + spotlight (target-anchored) | only during a session |
| 3 · Intelligence | arbitrary questions / custom goals | summoned composer (⌘K / "Ask") | zero until summoned |

Discovery is **recognition** (show named tasks + progress), never **recall** (a
blank input). The blank input exists only in Layer 3. That rule is the firewall
against drifting back into chatbot UX.

## Adaptive placement system (the core of M9.6)

Principle (ranked): **visible > safe (no occlusion/collision) > not support-coded.**
Bottom-center is the first candidate, not a religion.

### Inputs (all client-side, already available or cheaply probed)
- Viewport size + `env(safe-area-inset-*)`.
- Host fixed/sticky **edge elements**: scan for `position: fixed|sticky` nodes whose
  bbox hugs a viewport edge → record which edges are occupied and how thick
  (top bar, bottom nav, sticky footer, side rail).
- Known third-party widgets via heuristics (Intercom/Drift/Crisp containers,
  cookie-consent bars, generic large fixed bottom elements) → treat as occupied +
  "support-coded" zones.
- Interactive-element density per candidate zone (don't dock over a cluster of
  host buttons).

### Candidate slots, scored
Ordered preference, each scored — highest safe score wins:
`bottom-center → bottom-left → (left/right edge handle) → top-left`.
Bottom-right is excluded by default (support reflex + usually occupied) unless a
tenant explicitly tokenizes it.

Score = visibility bonus − occlusion penalty (intersects a host fixed bar / dense
cluster) − support-collision penalty (near a known support widget) − intrinsic
support-coding penalty (bottom-right). If no slot clears the safety threshold →
fall back to the **edge handle** (near-zero footprint) or, if configured,
host-anchor / host-trigger (no SDK chrome).

### Hazard handling (the cases that worried us)
| Hazard | Behavior |
|---|---|
| Sticky footer / bottom toolbar | bottom slots that intersect it are penalized → dock sits **above** the bar or moves to a clear slot |
| Support / chat widget present | avoid its zone entirely (occlusion + don't look like it) |
| Cookie banner (transient) | treat as occupied; when dismissed, re-evaluate and settle |
| Mobile bottom nav | bottom is sacred on mobile → see mobile regime below |
| "Feels like a video bar" | enforced at the **form** level: a compact rounded **pill** (ring + label + count), never a full-width bar, never media controls, never a "?" |

### Re-evaluation & stability
Re-score on resize / route change / when a host sticky element appears or
disappears — debounced. Relocate **only** if the current slot's safety drops below
threshold (hysteresis), and animate the move (the object travels) so it never
jitters. Cap relocations per page to avoid flapping. On a host full-screen
takeover/modal, auto-collapse until it clears.

### Mobile regime
On narrow viewports the anchored guidance card becomes a **bottom sheet** that
respects `safe-area-inset-bottom` (above OS home indicator + host bottom nav); the
resting dock becomes a small mark in a safe corner rather than a bottom bar.

## Form rules (the "not support / not utility bar" guarantees)
- Resting state is a **compact pill** (≤ ~210px), progress ring + product-set label
  + step count. Never full-width, never a bare icon-only bubble, never a "?".
- No text input at rest anywhere. Input is summoned only (Layer 3).
- Content = named tasks + progress. That content, not the location, is what reads
  as "guide."

## Config / token API
```
placement:      "auto" (default) | "bottom-center" | "bottom-left"
                | "bottom-right" | "top-center" | "anchor"
anchorSelector: string   // mount into a host element (host-integrated)
avoidSelectors: string[] // host nodes to never overlap (their footer/chat)
offset:         { x, y } // nudge + safe-area
mode:           "dock" (default) | "handle" | "host-trigger" // no SDK chrome
```
`"auto"` runs the scorer above; every other value pins. Theme tokens (M9.5)
already cover color/radius/density/light-dark.
